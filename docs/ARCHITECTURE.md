# Architecture

This is the Phase 1 design, updated to match what was built. It follows
Block Burst Magic's structure.

## Goals that shaped the design

- Rules must be **deterministic and testable** without a device.
- The game state is **authoritative**; animation only shows changes and
  never decides an outcome.
- Gameplay must **never wait** for animation, audio, saving or ads.
- Every level must be **provably solvable**.
- Every optional system (audio, ads, storage) must **fail safely**.

## Layers

```
ui/  (screens, widgets, tube painter, board view and pour animation)
  │ reads/drives
state/  GameController, ProgressController, SettingsController, AppServices
  │ uses
core/  pure Dart rules – no Flutter, no I/O, no clocks
data/  versioned documents in shared_preferences
services/  audio, haptics, ads (+consent), share, rating, reminders
```

| `core/board.dart` | Immutable board, pour rules, completion, encoding, validation |
| `core/game_state.dart` | One puzzle in progress: board, moves, undo history, hints, status |
| `core/engine.dart` | `pour`, `undo`, `restart`, `addTube`, hints: the only place state changes |

State management uses Flutter's built-in `ChangeNotifier` and an
`InheritedWidget` (`AppScope`), as in Block Burst Magic.

## Tube representation and rules

A **board** is a list of tubes; a **tube** is a list of colour ids listed
from the **bottom to the top**: `[5, 0, 0]` is blue at the bottom with two
reds on top. In text form (saves, level data) colours are letters `a`–`j`
and tubes are comma-separated: `faa,a,,`. Every tube has capacity 4.

A pour from tube *s* to tube *d* is legal when *s* ≠ *d*, *s* is not
empty, *d* is not full, and *d* is empty or has the same top colour. The
contiguous run of the top colour moves, as much as fits:
`amount = min(run, 4 − len(d))`. Players never choose the amount.

**Solved** means every tube is empty or full of one colour. (Each colour
has exactly four units, so every colour is then in a single tube; a tube
holding only one colour but not full does not count.)

The widget positions never decide anything: taps are mapped to tube
indices, and `GameEngine` applies the pour to the data model.

## Moves, undo and restart

A **move** is one successful pour. Invalid attempts change nothing and do
not count. **Undo** restores the previous board *and* its move count (so
the counter always equals the pours that produced the board on screen);
undos are counted separately for statistics and achievements. Undo is
unlimited in levels, Daily and Relax; some challenges limit it. History
keeps the last 400 positions. **Restart** returns to the exact starting
position, resets moves and clears history; hints left carry over (restart
never creates hints) and records are untouched.

## Levels, solver and proofs

Levels are generated by `tool/reference_model/gen_levels.py` and written to
`lib/core/level_data.dart`; full metadata is in
`tool/reference_model/levels.json` and a summary in `docs/LEVELS.md`.

1. **Deal**: shuffle 4 units of each chosen colour into full tubes, add
   the spare (empty) tubes. Reject deals with a completed tube or too few
   colour changes ("well mixed": runs ≥ 60 % of units). The generator
   starts from random deals rather than reverse-pouring from a solved state:
   reverse sequences tend to leave long single-colour runs (easy puzzles),
   and every shipped level is proven by search anyway.
2. **Prove**: exact A* finds a shortest solution. The heuristic is
   *runs − colours*: a pour lowers the number of single-colour runs by at
   most one, and a solved board has one run per colour, so it is admissible
   and consistent, and the first solution found is shortest. Positions are
   compared ignoring tube order. Only "useful" pours are tried (never out of
   a completed tube, never a single-coloured tube into an empty one, only
   the first of several empty tubes), which never loses a solution.
3. **Measure**: shortest solution length (*par*) and the share of 200
   random games that solve it. Within each group, levels are ordered by
   *par × (1 + 2 × (1 − random-play win rate))*, and groups add colours.
4. **Check**: no duplicates (tube order and, for ≤ 5 colours, colour
   relabelling ignored), stored solution replays to a solved board.

`test/core/levels_test.dart` replays all 300 stored solutions with the
Dart engine and re-solves a sample with the Dart solver, which must find the
same par. `test/core/reference_test.dart` checks the Dart solver against
golden results from the Python model (same solution and effort).

## Stars

For par *p*: 3 stars at most p + max(2, ⌈0.15p⌉) pours, 2 stars at most
p + max(5, ⌈0.5p⌉), otherwise 1. Par is a proven minimum, so the targets
are reachable, with a little room. Replays never lower a record.

## Hints

1. If the current board is on the stored solution path, the next stored
   pour is the hint (instant).
2. Otherwise a weighted A* search from the current board (40,000 positions
   at most), then an exact search (300,000) if needed, on a background
   isolate.
3. "This position can no longer be solved" is only shown when the search
   was exhaustive. If the budget ran out, the message says so honestly.

A hint is only spent when a pour was found. Each puzzle starts with one free
hint (three in Relax, none in no-hint challenges); more come from rewarded
ads.

## Daily Puzzle and Relax

- **Date convention:** the device's local calendar date, `YYYY-MM-DD`. A
  new puzzle appears at local midnight. Same date → same puzzle.
- **Daily:** seed = FNV-1a(`sandburstmagic-daily-<date>`), 6–8 colours by
  weekday cycle, 2 spare tubes. Up to 12 deals are tried; the first well
  mixed one that the solver solves is used (exact A*, weighted if that runs
  out) and its solution stored. If all fail (never seen), a bank level is
  used. Generated on a background isolate and cached for the day.
- **Rewards and streaks:** a date is rewarded once; the streak grows on
  consecutive dates. A puzzle started late can be rewarded until the end of
  the next day. If the device date goes backwards, rewards pause until it
  catches up. No server: no global rankings.
- **Relax:** numbered puzzles, seed FNV-1a(`sandburstmagic-relax-<n>`), 5–7
  colours, 3 spare tubes, same verification. Solving one moves on to the
  next number.

## Progression

- Player level: L → L + 1 costs 100 + 50 × (L − 1) XP.
- XP: first level solve 20 + 5 × stars (+5/10/20 for medium/hard/expert),
  replays 5 per new star (else 2); challenge 60 + 10 × tier (replays 10);
  daily 80 + 5 × streak (streak counted to 10); relax 8; achievements 25–200.
- Themes: Moonlit Potion and Clear Crystal from the start; Mermaid Lagoon
  at player level 3, Fairy Spring at 6, Golden Elixir with a 3-day daily
  streak, Bubblegum Fizz after 12 challenges, Frozen Spell at player level
  10, Ruby Ember with a 7-day daily streak. Themes change glass and
  background only. (Internal ids, used in saved settings: midnight,
  minimal, ocean, aurora, sunset, candy, frozen, ruby.)
- Bottle shapes: Tube, Bottle, Flask, Jar and Potion from the start; Vial
  at player level 8, Teardrop after 24 challenges (`ShapeUnlocks` in
  core/progression.dart). A shape that isn't earned (for example after a
  progress reset) falls back to the Tube.
- No currencies, no purchases, nothing pay-to-win.

## Persistence

`shared_preferences` holds separate JSON documents (`sbm.*` keys):
settings, progress, ad frequency state, review state, the cached daily
puzzle, and one puzzle in progress per mode (classic, relax, daily,
challenge). Each is stored as `{"v": version, "data": {...}}` and handled
by `DocStore` (from Block Burst Magic): migrations, validated writes (a
value is encoded and parsed back before it replaces a save), a `.bak`
backup of the last good copy, tolerant parsing, newer-version data never
overwritten, asynchronous ordered writes.

Saved puzzles are checked strictly when loaded: the stored solution must
solve the stored start, and the saved board must contain exactly the same
liquid as the puzzle. Anything inconsistent is not offered for resume.

When saved: the puzzle in progress after every pour/undo/restart and when
the app is hidden; progress shortly after changes (coalesced) and at once
when the app goes to the background; settings on every change. Replays of
already solved levels are not saved, so they never replace the level being
worked on.

## Animation

- The board is one `CustomPainter` behind a `RepaintBoundary`, repainted by
  a `Ticker` that **stops when nothing moves** (no idle animation except a
  shown hint's pulse).
- **Liquid levels are computed from area**: the interior is a polygon
  (rounded bottom included); a band's top is found by binary search so its
  area equals its units. This keeps units equal in the round bottom and
  keeps surfaces horizontal while a tube tilts.
- A pour: the source (already lifted) moves over the destination and tilts
  towards it (230 ms), liquid flows with a stream (200 ms + 90 ms per unit),
  then the tube returns (220 ms). Several pours can run at once; tubes in a
  running pour ignore taps. Undo/restart cancel animations.
- Selection: lift, violet outline glow and a chevron above the tube.
  Completed tubes get a stopper. Refused pours shake the target tube.
- Reduced motion (switch or system setting): no movement or tilt, short
  level change, no sparkles or celebration.

## Major technical risks (and mitigations)

| Risk | Mitigation |
| --- | --- |
| Code first compiled in CI, not locally | Same CI as Block Burst Magic; nothing is reported as passing without a log |
| Unsolvable or broken levels | Exact A* proof per level in Python, replayed in Dart; Dart solver re-checked against golden vectors |
| Animation desync / double pours | State changes at once; animations read state; busy tubes ignore taps |
| Hint search slow on big levels | Stored-path shortcut, weighted search, background isolate |
| Lost progress | Validated writes, backups, versioning, saves on background |
| Ads hurting play | Never during a puzzle; conservative caps; nothing waits on ads |
| Policy changes (Play/AdMob) | Requirements to re-verify are listed in `docs/PUBLISHING.md` |
